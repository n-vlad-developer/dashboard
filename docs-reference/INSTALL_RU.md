# Установка на Windows / NSSM

## 1. Подготовка

Сделать резервную копию PostgreSQL и текущего backend. Сначала проверить обновление на отдельной копии БД и отдельном Redis/окружении. Во время замены остановить Django, Celery worker и Beat, чтобы старый код не работал с новыми моделями.

Скопировать содержимое `backend/` поверх `D:\mindtech-horeca-core\backend`. Существующие `.env`, media и настройки IIS остаются на месте. Архив не содержит новых ключей или секретов. Не выполнять `makemigrations` на рабочем сервере: необходимые миграции приложены.

Активировать используемый venv. Список зависимостей, присланный в чате, неполный: код также импортирует `firebase-admin` и `openai`, а QR-админка требует `resvg-py` и `zxing-cpp`. Сверить установленное окружение через `python -m pip check`. Файл `docs/tested-packages.txt` фиксирует версии пакетов в тестовом окружении; это не замена production requirements и не команда обновить все библиотеки.

## 2. Миграции и проверка

Из каталога backend, с прежними настройками подключения:

```powershell
.\.venv\Scripts\python.exe manage.py showmigrations
.\.venv\Scripts\python.exe manage.py migrate --plan
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py collectstatic --noinput
```

Новые таблицы dashboard содержат политики доступа, график, задания и сессии. Call получает снимки состава смен и порогов; код статуса `arrived` сохраняется, подпись меняется на «Принят». Сохраняются миграции v6.

В исходной notifications/0003 исправлена зависимость: очистка использует поле platform из 0002, поэтому теперь зависит от 0002. На БД, где обе миграции применены, очистка повторно не запускается. Если обнаружится необычная история, где 0003 применена, а 0002 нет, не применять `--fake`: сначала проверить реальную схему и историю на копии БД.

## 3. Службы NSSM

Один экземпляр Beat. Основной worker обслуживает обычную очередь, новый worker — тяжёлые задания.

| Служба | Path | Arguments |
|---|---|---|
| horeca-celery | D:\mindtech-horeca-core\backend\.venv\Scripts\celery.exe | -A horeca_core worker -l info -P solo -Q celery -n realtime@%h |
| horeca-celery2 (Beat) | тот же celery.exe | -A horeca_core beat -l info |
| horeca-background (новая) | тот же celery.exe | -A horeca_core worker -l info -P solo -Q q1_background -n background@%h |

Startup directory для всех: `D:\mindtech-horeca-core\backend`. В поле NSSM Arguments вставлять строку как есть; `%h` — подстановка Celery. Использовать прежнего сервисного пользователя и окружение. Добавить вывод stdout/stderr в отдельные журналы средствами NSSM.

Роутинг в settings/base.py направляет dashboard.run и apps.analytics.tasks.refresh_venue в q1_background. Без этого worker переводы и пересчёты останутся в очереди. Старые задачи других модулей сохраняют обычную очередь.

Beat: диспетчер dashboard и проверка таймеров вызовов — раз в минуту; проверка завершения смен — раз в минуту; обновление аналитики — раз в 10 минут. Это плановая периодичность, а не гарантия исполнения в точную секунду: учитываются очередь, доступность Redis/БД и процессов.

## 4. Настройка заведения

В главной админке карточка заведения → «Доступ, права, лимиты переводов и график работы».

- Включить кабинет. Только действующие сотрудники с ролями admin/director; `must_change_password` должен быть снят штатным процессом активации аккаунта.
- Администратор привязан к своему заведению; директор — к `allowed_point_of_sales` своей сети. Пустой список директора не означает доступ ко всей сети.
- Меню доступно обеим ролям. Аналитику и AI-перевод включать отдельно для каждой роли.
- Для регулярного формирования отчётов у заведения также включить существующее `analytics_enabled`.
- AI-перевод по умолчанию выключен. Настроить месячное число заданий и лимит «символы исходника × число языков». Нулевой лимит запрещает новые задания.
- Для расписания включить автозакрытие по графику и заполнить все семь дней: 0=Пн, 6=Вс. Выходные отметить явно. 09:00–01:00 означает закрытие следующей ночью; запас 15 минут даёт срок 01:15. Равные начало и конец означают 24 часа.
- Если график выключен либо смена открыта вне подходящего рабочего интервала, действует прежний ограничитель длительности смены. Изменение расписания распространяется и на ещё открытые смены.
- Таймер просрочки — `call_expire_minutes`; таймер автозакрытия после принятия — `call_auto_close_minutes`. Новые вызовы сохраняют значения при создании; изменение настроек не меняет их снимок. Для старых записей без снимка используются текущие настройки.

AI использует существующие OPENAI_API_KEY и AI_MENU_MODEL. `.env` менять не требуется, если они уже настроены и модель поддерживает существующий в проекте Responses API с JSON-ответами. Реальный платный запрос при подготовке архива не выполнялся.

## 5. Пересчёт и проверка перед запуском

Главная админка → Кабинет заведения → Фоновые задания кабинета → «Пересчитать всю аналитику», подтвердить. Дождаться completed; processed/total показывают обработанные дни. В конце пересчитываются смены и существующие отчёты за период. Общий пересчёт охватывает заведения с analytics_enabled=True, начиная с самой ранней доступной записи. Ошибка оставляет уже рассчитанные дни и показывает failed; подробности в журнале worker.

Проверить на тестовом заведении: вход admin/director; запрет доступа к чужому ID; изменение меню; отключение аналитики; вызов → просрочка → принятие → ручное/системное закрытие; запрет закрытия другим сотрудником; смену, открытую в обед и закрываемую в 01:15; успешный отчёт версии 7.

Для фронтенда с отдельного домена отдельно проверить действующий CORS. PATCH использует заголовок If-Match, перевод — Idempotency-Key: они должны быть разрешены CORS. Применённое обновление добавляет эти заголовки в настройки; список разрешённых доменов остаётся вашим.

Откат после миграций: восстановить совместно копию backend и БД. Не удалять таблицы и историю на работающем сервере.
