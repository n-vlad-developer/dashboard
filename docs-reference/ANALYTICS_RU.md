# Контракт API аналитики v1

Базовый путь: `/api/analytics/`. Авторизация: существующий `Authorization: Bearer <access_token>`.

## Запросы

`GET /api/analytics/venues/` — доступные заведения, `id`, `name`, `timezone`, `analytics_enabled`.

`GET /api/analytics/venues/2/dashboard/?start=2026-10-01&end=2026-11-01&granularity=day`

`start` включительно, `end` исключительно, обе даты в часовом поясе заведения. По умолчанию последние 7 календарных дней включая текущий. Максимум 366 дней. `granularity=half_hour` доступна до 7 дней. `day` отдаёт графики по дням для вызовов, гостевых заказов, жалоб, заказов и климата. `half_hour` — график вызовов и рабочего времени.

401 — нет JWT; 404 — нет доступного заведения; 400 — неверные даты/детализация; 503 — неверно настроен часовой пояс. Все запросы только читают готовые данные; до расчёта возвращаются пропуски, а не выдуманные нули.

## Структура

| Поле | Назначение |
|---|---|
| `schema_version` | Версия публичного контракта, сейчас 1 |
| `calculation_version` | Версия формул, сейчас 7 |
| `metric_definitions` | Названия, единицы и определения основных показателей |
| `venue` | Заведение и его часовой пояс |
| `period` | Границы диапазона и детализация |
| `freshness` | Время расчётов, полнота, пропущенные дни, признак ошибки обновления |
| `summary` | Карточки: вызовы, принятия, закрытия, просрочки, время реакции, часы персонала |
| `comparison` | Предыдущий диапазон той же длины, его полнота, абсолютные и относительные изменения |
| `series` | Ряды для графиков. Пропущенный день: `state=missing`, `metrics=null` |
| `staff` | Сотрудники с фактическими принятиями и рабочим временем |
| `tables` | Столы и залы с вызовами, реакцией, просрочками |
| `categories`, `sources` | Данные для диаграмм по категориям вызовов и источникам |
| `guest` | Сессии, языки, заказы, статусы, позиции, запросы счёта, предпочтения оплаты |
| `complaints` | Число жалоб, причины, текущие статусы |
| `orders` | Открытые в периоде заказы и отдельно оплаченные закрытые в периоде |
| `climate` | Min/max и средняя температура/влажность по измерениям |
| `quality` | Некорректные времена, незакрытые смены, принятия без сотрудника, пересечение смен |
| `notes` | Пояснения к трактовке данных |

## Метрики и трактовка

Все вызовы относятся к **дате создания**, включая административные категории. `arrived_at` — принятие вызова сотрудником (свайп в режиме без меток). Это не доказательство физического подхода к столу. В исторических записях режима меток смысл зависел от действовавшего клиента. Реакция: `arrived_at − created_at`, только неотрицательные значения. Неверные времена исключаются из среднего и учитываются в `invalid_reactions`. Среднее периода считается из общей суммы секунд и числа реакций; средние дневных средних не используются.

`calls_arrived`, `calls_expired` и `calls_closed` пересекаются: вызов мог просрочиться, затем быть обработан и закрыт. **Не используйте эти поля как взаимоисключающие сектора круговой диаграммы.** Для секторов подходят `categories` и `sources`. `calls_open + calls_closed = calls_total`; `calls_auto_closed` — подмножество `calls_closed` при существующем наборе статусов. Автозакрытие не означает подтверждённое обслуживание.

Часы персонала — объединение всех интервалов смен каждого сотрудника в периоде, обрезанных границами дня и временем расчёта. Пересечения двух смен одного сотрудника не удваивают часы. Перерывы не учитываются, поскольку в источнике нет их интервалов. Учитываются все имеющиеся роли: это показатель часов персонала, а не исключительно официантов. Вызовы на час — все вызовы / эти часы.

Строки `staff` используют фактического `staff_arrived`. Если он не указан, вызов попадает в строку `id=null`. Это позволяет сумме вызовов по строкам совпадать с итогом без приписывания необработанных вызовов случайному сотруднику. Детальные строки смен требуют совпадения и Call.shift, и принимающего сотрудника; не складывайте группировки смен и сотрудников между собой.

`null` у среднего или отношения — нет знаменателя. Настоящий ноль остаётся 0. Нет ни одного готового дня — `summary`, `guest`, `orders`, `complaints` равны null, массивы пустые. При частичном диапазоне итог относится только к доступным дням, что отражено в `freshness`.

Текущий день имеет `state=partial`. В получасовом ряду будущие относительно времени расчёта интервалы имеют `observed=false`; отображайте их как будущие, не как фактический ноль. При DST число интервалов может отличаться от 48; опирайтесь на start/end с UTC-смещением. Не группируйте только по тексту «02:30».

`comparison.comparable=true` только когда оба диапазона полностью рассчитаны и текущий день не входит в сравнение. Процент изменения при нулевой базе — null, абсолютное изменение остаётся доступным. Увеличение количества вызовов не обязательно улучшение, уменьшение реакции обычно улучшение; оформление определяет фронт.

## Гостевые данные и деньги

Сессия — запись GuestSession, **не уникальный человек**. Система сейчас не сохраняет отдельные события просмотра меню/блюда и кликов такси/соцсетей, поэтому просмотры и конверсия кликов не возвращаются.

`guest.orders` — все созданные гостевые заказы. `noncancelled_orders` и `noncancelled_amount` исключают текущий статус cancelled. `average_order_amount` — средняя сумма такого заказа, не средний оплаченный чек. Сумма берётся из сохранённого `GuestOrder.total` и включает то, что уже включено в total источником. `products` — количество и сохранённая сумма строк неотменённых гостевых заказов; не включает отдельной строкой процент обслуживания. Строки группируются по id блюда и сохранённому названию, поэтому переименование не склеивается молча.

`orders.opened` и `orders.statuses` относятся к opened_at. `paid_closed_count` и `paid_closed_amount` относятся к closed_at и требуют `is_paid=True`, `status=closed`. Эти записи могут пересекаться с гостевыми заказами. **Две суммы не складывать.** Это данные локального модуля заказов, не сверенный фискальный отчёт и не бухгалтерская выручка.

Денежные значения — строки Decimal с двумя знаками. Валюта в исходных моделях не хранится; не добавлять автоматически KZT без согласованной настройки заведения. `payment_preferences` — выбранный метод в запросах счёта, не подтверждённые оплаты.

Климат: среднее взвешено по числу измерений, а не по длине интервалов между ними. Если датчик пишет нерегулярно, это средняя измерений, не средневременная температура.

`quality.open_shifts` суммирует незакрытые смены по дням: одна длинная смена может учитываться в нескольких днях. Это число дневных наблюдений, не уникальных смен за период. Флаг `refresh_failed` показывает ошибку фонового цикла, а `oldest_calculated_at` позволяет оценивать возраст данных самостоятельно.

## Ограничения исторической точности

Исторические имена столов/залов и профили сотрудников могут меняться. Полного неизменяемого журнала этих справочников в проекте нет. Удаление стола каскадно удаляет его вызовы в исходной модели, и восстановить их аналитикой невозможно. `active_tables_now` в суточном snapshot — состояние справочника на момент пересчёта, не историческая загрузка столов. Поэтому процент занятости и условная нагрузка 0–100 не выдаются.

Индексы старой нагрузки и оценки остались в схеме только для совместимости; новые расчёты не используют их. Старый `load_index_0_100=0` после пересчёта v7 не является измеренной нулевой загрузкой. Фронт должен использовать новый API, а не эти поля.

## Использование на фронте

1. Получить список доступных заведений.
2. Выбрать id и диапазон; запросить dashboard.
3. Карточки строить по summary, подписи/единицы — metric_definitions.
4. График вызовов: series[].date и series[].metrics.calls_total; пропуски не соединять с нулём.
5. Диаграмма категорий: categories[].name и calls_total.
6. График суммы гостевых заказов: дневные series[].guest.noncancelled_amount; перевести в числовой тип только для рисования.
7. Таблицы сотрудников, столов, блюд — соответствующие готовые массивы. Входные имена отображать как текст, не HTML.
8. Показывать доступные/ожидаемые дни, текущий неполный день, время расчёта и ошибку обновления.

Редактирование меню и чтение аналитики из кабинета описаны в API_RU.md. Управление доступом и расписанием остаётся в главной админке.

## Снимки вызовов и качество оценки персонала

Новый Call сохраняет roster_snapshot — открытые смены сотрудников своего заведения при создании, независимо от списка push-получателей; timing_snapshot — пороги и режим. API calls отдаёт эти поля как staff_at_creation и timing. Для старых записей снимков нет: history_complete=false; пересчёт не восстанавливает недостающие факты. Массовое создание через bulk_create обходит model.save и не создаёт снимков: новые интеграции должны использовать штатное создание Call.

Просрочка сохраняется в expired_at после принятия и закрытия. Просроченный вызов остаётся доступен для обслуживания. Системное закрытие отсчитывается от arrived_at. Только staff_arrived может закрыть вручную; система не записывается как человек в staff_closed. Завершение оплаты и завершение последней смены больше не закрывают ожидающие вызовы. Таймеры применяются к категориям 10, 11, 15, 20, 30.

Для сравнения сотрудников используйте часы, принятые вызовы, вызовы на час, среднее/медиану/P90 принятия и число принятых просроченных вызовов. Последний показатель не доказывает вину принимающего: он мог подхватить уже просроченный вызов. Автоматическое закрытие не даёт достоверной длительности реального обслуживания. Единого балла «качества официанта» из этих данных не вычисляется.

При автоматическом закрытии смены closed_at равен расчётному сроку (конец рабочего дня плюс запас), даже если worker выполнил задачу позднее. Отработанные часы включают запас и не вычитают перерывы. Смена, открытая в обед, получает меньше часов, но тот же срок окончания рабочего дня.
